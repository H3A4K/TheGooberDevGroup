3. Purpose

The app is to redesign the restaurant's website to be more modern and follow traditional design principles. We will have a menu that will list all the items and a large description with a button to add to cart, an ordering page that will show a shorter description and ability to add to cart, and a cart that will allow the user to place their order with the restaurant.

There will also be an accounts system to allow users to see their previous orders. Customers will use the site to browse menu items, add items to their cart, select between pickup/delivery, create an account, apply promo codes for discounts, and place orders online. Clarence's Kitchen will use the site to present a more modern brand image of themselves and manage promotions through promo codes.

We have chosen to take on redesigning their site, as the current one is outdated and does not follow traditional design principles. Ometh would like a modern site to draw in more customers. We will also make the site responsive, so that customers can use either their phones or their computers to place an order, which is currently not supported properly on their current site.


4. Data Description

Table 1: User Accounts Revised

We need this table to store the different customer's login details as well as any other information about their account. The information that will be stored is email, password, phone number, address, number of orders, and an admin flag that gates access to the admin pages.

Fields: userid (number), email (text), password (text), phonenumber (text), address (text), ordersdone (number), admin (boolean). Primary key will be accountId.

Field Type
accountId number
email text
password text
phonenumber text
address text
ordersdone number
admin boolean (default 0)

Added an admin boolean column so the same accounts table can back both customer and administrator accounts. Every admin page (/admin/*) checks this flag before rendering; setting admin = 1 on a seeded user is how we grant access to the admin panel during testing.

Table 2: Products Revised

We need this table to easily get a list of all the available products that the customer is able to order. The information that will be stored is product name, product description, the filename of an uploaded product image, and price.

Fields: productid (number), productname (text), productdesc (text), price (float), productImg (text, filename in assets/images/menu/), productClass (text). Primary key will be productid. productClass is a foreign key that references productClasses.name (see Table 6 below).

Field Type
productId number
productName text
productDesc text
price float / Number
productImg text (filename only)
productClass text (FK → productClasses.name)

Admins can now upload PNG or JPG images for each menu item through the Products admin page. Uploads are validated server-side via getimagesize(), capped at 5 MB, and stored with a collision-safe server-generated filename (e.g. product_65f3abc.png) under assets/images/menu/. The database stores only the filename in productImg; the frontend prepends the image directory path when rendering.

productClass has also been promoted to a proper foreign key linking into the new productClasses taxonomy table so categories can be administered centrally instead of being free-text per product.

Table 3: Orders Revised

We need this table to get a list of all orders that were ordered, including past orders for order history. The information that will be stored is the account that ordered, the address to deliver to if its delivery, the date it was ordered, whether the order is being fulfilled as pickup or delivery, and whether the order has been fulfilled, along with the promo discount that was actually applied to the order at checkout. The individual items in each order are stored in the OrderDetails table (see below), following proper database normalization principles (similar to the Northwind sample database on W3Schools).

Fields: orderId (number), accountId (number), orderDate (text), address (text), fulfillmentMethod (text, "pickup" or "delivery", default "pickup"), fulfilled (boolean), discountTotal (float, promo discount stamped at checkout). Primary key will be orderId. Foreign key accountId references User Accounts.

Field Type
orderId number
accountId number
orderDate text
address text
fulfillmentMethod varchar(20) NOT NULL default 'pickup'
fulfilled boolean
discountTotal float / Number

Added fulfillmentMethod so each order explicitly records whether it is a pickup or a delivery rather than trying to infer that from the address string. The customer picks between the two on the checkout panel before placing the order, and the new pickup confirmation page uses this flag to switch between "Estimated Wait Time" (pickup) and "Estimated Delivery Prep Time" (delivery) labels and to only show the delivery address block when relevant.

Added discountTotal to persist the promo discount that was actually applied at checkout, so the order record matches exactly what the customer saw in their cart. The value is computed server-side in complete_order.php via the new calculateOrderDiscountTotal() helper (using the same percentage-vs-fixed rules as get_cart.php) and stamped onto the order row as part of the checkout transaction.

Both columns are written with runtime SHOW COLUMNS guards (ordersHasFulfillmentMethodColumn() and ordersHasDiscountTotalColumn()) in complete_order.php so the app still runs cleanly against older databases that haven't been migrated to the new schema; discountTotal in particular is persisted via a separate follow-up UPDATE specifically so the primary fulfillment update stays identical on unmigrated databases.

Table 4: OrderDetails

This junction table links orders to the products they contain, rather than storing a list of items directly in the Orders table. Each row represents one product line in an order, with a quantity field. This follows the same pattern as the OrderDetails table in the Northwind sample database.

Fields: orderDetailId (number), orderId (number), productId (number), quantity (number). Primary key will be orderDetailId. Foreign key orderId references Orders, foreign key productId references Products.

Field Type
orderDetailId number
orderId number
productId number
quantity number

Table 5: PromoCodes Revised

This table stores promotional codes and discounts that can be applied to orders. Promo codes are entered by the customer at checkout and validated against this table. When a valid promo code is applied, the discount is calculated and deducted from the order total in the cart before the order is placed. Admins can create, modify, and deactivate promo codes through the admin interface. A promo code can optionally require specific products to be in the customer's cart before it applies (see the new requiredProductIDs column below).

Fields: promoId (number), promoCode (text), discountType (text), discountValue (float), active (boolean), expiryDate (text), requiredProductIDs (text, comma-separated product IDs, optional). Primary key will be promoId. The discountType field is either "percent" or "amount", which determines how discountValue is applied (e.g. 15% off vs. $5 off).

Field Type
promoId number
promoCode text
discountType text ("percent" or "amount")
discountValue float / Number
active boolean
expiryDate text
requiredProductIDs text (comma-separated IDs, NULL = no requirements)

Added requiredProductIDs so a promo code can be restricted to orders that include specific menu items; e.g. the seeded WINGSFRIES code only applies when both Classic Battered Fried Wings (101) and CK Loaded Fries (104) are in the cart. If the field is NULL the code behaves like a universal discount.

Validation happens in three places to prevent tampering: (1) when the customer clicks Apply (server returns a descriptive error naming any missing items), (2) on every cart refresh (a stale code whose required items were removed is silently dropped), and (3) again at order completion (complete_order.php) as a final server-side guard before the order is marked fulfilled.

Table 6: ProductClasses New

Introduced so menu item categories (CK Favourites, Side, Drink, Salad, etc.) are managed centrally instead of being typed as free text on every product. Each row is one category; products link to a category via the products.productClass foreign key.

Fields: classID (number), name (text, unique), quantity (number), time (decimal). Primary key will be classID.

Field Type
classID number (auto-increment)
name varchar(255) UNIQUE
quantity number
time decimal(5,2)

Seeded with four rows matching the live menu structure: CK Favourites, Side, Drink, and Salad. The menu page uses these to populate its category filter checkbox list, and the Products admin uses them to populate the "Product Class" dropdown when creating or editing a product.

Table 7: Promotions New

Added to drive the promotional banners displayed at the top of the menu page (see the Menu Page notes in Section 5). Each row is one visual promo card with its own title, eyebrow label, price display, badge, description, fine print, theme color, banner image, and an optional promo code the customer can copy into the cart. This is deliberately separate from the PromoCodes table (a Promotion is marketing content, a PromoCode is redeemable logic), and admins manage them from two distinct admin pages.

Fields: promotionID (number), title (text), eyebrow (text), price (text, display-formatted, e.g. "$22.99"), badge (text), description (text), finePrint (text, one rule per line), image (text, filename), theme (text, one of orange/brown/green/blue), ctaLabel (text), active (boolean), sortOrder (number), promoCode (text, optional). Primary key will be promotionID.

Field Type
promotionID number (auto-increment)
title varchar(255) NOT NULL
eyebrow varchar(100)
price varchar(50) (display text)
badge varchar(100)
description text
finePrint text (newline-separated rules)
image varchar(255) (filename)
theme varchar(20) default 'orange'
ctaLabel varchar(50) default 'Order Now'
active boolean default 1
sortOrder number default 0
promoCode varchar(50) (optional, for display)

Seeded with two banners to demonstrate the feature on a fresh install: Wings & Fries ($22.99, orange theme, linked to the WINGSFRIES promo code from Table 5) and Pick 3 Favourites ($39.99, brown theme, linked to the PICK3 promo code). Admins can add/edit/deactivate them through the dedicated Promotions admin page (/admin/managepromotions.html), including uploading banner images.

Shopping Cart Revised

The shopping cart will be managed client-side using the browser's localStorage. Cart data (product IDs and quantities) is stored as a JSON object in localStorage, so the cart persists across page navigations and browser sessions on the same device. When the user places an order, the cart contents are sent to the server, which creates the Order and OrderDetails entries in the database, and the cart is cleared from localStorage.

The shopping cart is tracked server-side on the existing Orders / OrderDetails tables rather than in browser storage. When a logged-in customer adds their first item, an Orders row is created with fullfilled = 0; that "open order" is the user's cart. Subsequent adds become OrderDetails rows tied to the same order. Cart reads, removes, promo apply/remove, and checkout all operate on this open order. Completing the order flips fullfilled to 1 and any applied promo code is cleared from the session so the next cart starts fresh.

We moved away from localStorage for three reasons: (1) it let us validate cart contents server-side when applying conditional promo codes (see Table 5), (2) it survives the customer switching devices as long as they're logged into the same account, and (3) it gave us a single source of truth, since admins viewing the Orders page see the same data the customer sees in their cart.

Relevant endpoints: assets/php/add_to_order.php, get_cart.php, remove_from_order.php, apply_promocode.php, remove_promocode.php, and complete_order.php. The applied promo code lives in $_SESSION["appliedPromoID"] while the cart itself lives in the database.


5. Functions Performed by the App Revised

Customer Functions

  • Sign Up/Login Page
    • INSERT/UPDATE to database on signup
    • SELECT from database on login
  • Account Page Revised
    • SELECT from accounts table to pre-fill the current email, phone number, and address into the update form so the customer can see their existing values before editing
    • UPDATE accounts table through changecredential.php when the customer saves a new value
  • Product/Ordering page
    • SELECT from database for products
    • SELECT from promotions table (where active = 1) to render promotional banners above the menu grid
    • SELECT from productClasses to build the category filter checkbox list
  • Cart Page Revised
    • Cart contents stored and managed in browser localStorage (client-side)
    • Cart contents are tracked server-side as an open Orders row (fullfilled = 0) plus its OrderDetails; the customer's login session ties the cart to them
    • INSERT into OrderDetails (and create a new Orders row on first add) through add_to_order.php
    • DELETE individual items through remove_from_order.php (single-item remove button on every cart row)
    • SELECT from PromoCodes table to validate and apply promo codes at checkout (apply_promocode.php, including the new requiredProductIDs check against the current cart)
    • Clear the applied promo through remove_promocode.php when the customer clicks the × on the applied-promo chip
    • UPDATE Orders table to flip fullfilled = 1 on checkout; the same statement also stamps the customer's chosen fulfillmentMethod (pickup or delivery) and the final address on the order row. The server re-verifies the applied promo code's requirements one last time before finalizing
    • A follow-up UPDATE on Orders stamps discountTotal (the promo discount actually applied, computed server-side with the same percentage-vs-fixed rules as the cart display) so the order record exactly matches what the customer saw at checkout. Both writes are guarded by SHOW COLUMNS checks so the app still works against databases that predate the new columns
  • Search all keywords of items from entire website
    • SELECT from database for products
  • Pickup / Delivery Confirmation Page Revised
    • Customer-facing confirmation view that the user lands on immediately after checkout (/pickup/?order_id=N), showing an estimated wait time, an itemized breakdown of the order that was just placed, and the delivery address when applicable
    • SELECT from Orders + OrderDetails + Products (joined in assets/php/pickup.php) to build the itemized order summary table with columns Product Name, Quantity, Price Per Unit, and Price, followed by Subtotal / Discount / Tax (13%) / Total rows
    • SELECT from ProductClasses to compute the estimated wait time server-side: items are grouped by their product class, the per-class time field drives the estimate, and the result is rounded up to the nearest five-minute mark
    • Reads orders.fulfillmentMethod to swap the time-card label between "Estimated Wait Time" (pickup) and "Estimated Delivery Prep Time" (delivery), and to only render the delivery-address block for delivery orders
    • Reads orders.discountTotal: the Discount row is hidden when the persisted value is exactly 0.00, and shown with a leading “−” prefix when a promo discount was applied
    • Returns 401 for unauthenticated visitors and 404 when no matching order exists for the signed-in account, so other users cannot view each other's confirmation pages by guessing IDs

The cart is now a first-class database concept rather than a client-side blob, which made it straightforward to implement cart item removal, conditional promo codes, and server-side re-validation at checkout time. The page flow is unchanged from the customer's perspective; only the storage layer moved.

9. Client Feedback

Based on the client’s feedback, we adjusted the project plan to make smooth, modern user interface, using the orange, black, and white colour scheme as Ometh said:
"Overall we just want something sleek and professional looking, like the one right now is kind of unprofessional looking you know?".

Ometh also requested that we add an accounts system as
"Having accounts would be super helpful as we could promote the restaurant through newsletters and promotions as well as keep track of customer data to see what menu items are trending."

Additionally, we will be displaying promotions on the menu as Ometh told us:
"We have lots of deals, especially buy 1 get 1 and student combos that we like to promote, so being able to see those on the menu page is really important."

The final change that Ometh requested was having a way to place orders directly with them, instead of redirecting them to UberEats, as they
"Currently have it setup so that it redirects customers to UberEats, but would like an actual in-store site".

All of these changes have already been reflected in the development plan outlined above.
